# Build and deploy

A `create-exo-app` project produces static HTML, JavaScript, and assets. Deploy the production output, not the source tree or the development server. No ExoJS server process is required for a client-only application; any backend services your game uses remain a separate concern.

## Verify the production output

```sh
npm run build
npm run preview
```

The build writes `dist/`. Preview serves that output locally so you can check compilation and asset paths. It does not reproduce every production header, cache rule, MIME mapping, or cross-origin policy. Check the deployed URL as well.

Use the lockfile and pinned compatible package versions in CI. Run the project's typecheck and tests before publishing. Serve the result over HTTP or HTTPS rather than opening `index.html` with `file://`.

## Configure a subdirectory deployment

Vite's `base` controls generated bundle URLs. A site hosted at `/my-game/` needs a matching base before building:

```ts no-check -- this is the consumer project's Vite configuration, not the engine TypeScript program
import { defineConfig } from 'vite';

export default defineConfig({
  base: '/my-game/',
});
```

Vite does **not** rewrite every arbitrary string passed to an asset loader. Resolve the loader's base from the deployment base as well:

```ts no-check -- import.meta.env.BASE_URL is supplied and typed by Vite in the consumer project
import { Application } from '@codexo/exojs';

const deploymentBase = new URL(import.meta.env.BASE_URL, document.baseURI);
const assetBase = new URL('assets/', deploymentBase).href;
const app = new Application({ loader: { basePath: assetBase } });
```

Add the scene and canvas options from your application entry point; the fragment above isolates URL configuration. A descriptor such as `image/hero.png` then resolves below that asset base. Do not prefix it again with `assets/` or `public/`.

Files under `public/` are copied unchanged. Imported assets follow the bundler's asset pipeline. Check exact filename casing and ensure that a missing asset returns a real failure rather than the host's HTML application fallback.

## Choose a host

Use a static host that can serve the entire output with correct relative paths and headers. For an embedded HTML game, package the contents of `dist/` at the archive root and configure the embedding surface to match the application's sizing policy.

For GitHub Pages or another CI-based host, use its maintained deployment workflow and publish only after the build succeeds. Keep hosting credentials in the host's secret store, not in application JavaScript. A browser bundle cannot keep a secret from its user.

Verify JavaScript MIME types, font and media responses, HTTPS, and any required CORS headers. Both `text/javascript` and other standards-compatible JavaScript MIME types can be valid; an HTML fallback or `text/plain` response for a module is a common failure.

## Using a release bundle without a bundler

Core provides ESM and classic-script bundles. Prefer a bundler-based project for dependency resolution and tree shaking; importing selected names from an already bundled browser module does not make the browser download only those exports.

For a classic script, copy a specific release's Core bundle into your deployed files:

```html
<script src="./vendor/exo.iife.min.js"></script>
<script>
  const { Application, Scene } = Exo;
</script>
```

The Core-only bundle is `exo.iife.min.js`. `exo.full.iife.min.js` contains Core and the official runtime packages except React on the same `Exo` global. Choose one; do not load separate independent Core copies together. The full bundle includes APIs, but package-specific systems and application configuration still need to be used correctly.

For browser ESM, the debug bundle is external-Core and needs `@codexo/exojs` resolved to the same Core module, for example through an import map. Keep the map, engine, debug module, and optional packages version-aligned. Avoid unversioned CDN URLs in a reproducible production deployment.

## Policies and optional features

Test the application's actual capability requirements. Automatic backend selection does not supply a missing shader language, unsupported target format, or raw WebGPU implementation of your own code. Surface a useful startup or feature-disabled state instead of leaving a blank canvas.

A Content Security Policy must permit the resources the application actually uses. Blob-backed workers and worklets require particular policy allowances; use [Typed worklets and workers](/ExoJS/en/guide/shipping/typed-worklets-and-workers/) for that boundary rather than adding broad allowances speculatively.

Audio needs a user-gesture path. Fonts and cross-origin media need successful requests and appropriate access. Persistent asset storage is not an application-shell service worker; [Offline and caching](/ExoJS/en/guide/assets/offline/) explains what the loader does and does not make available offline.

## Final smoke test

Check the deployed production URL on representative devices: first load, refresh on the intended route, resize, input focus, audio unlock, scene navigation, and return from a hidden tab. Exercise a failed asset and unsupported optional capability deliberately. Inspect the Network panel for missing or unexpectedly repeated requests.

When embedding in a framework, let the host own its DOM and destroy the application when the host is permanently removed. Await asynchronous application teardown where the hosting API permits it, and handle its rejection at that boundary. See [React integration](/ExoJS/en/guide/integrations/react/) for the maintained React host.

Use [Troubleshooting](/ExoJS/en/guide/shipping/troubleshooting/) for failures and [Performance](/ExoJS/en/guide/debugging/performance/) for measurements. Deployment is complete when the real hosted application works, not merely when a local build command exits successfully.
