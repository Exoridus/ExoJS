# Shader files and build validation

A shader-taking API receives source text. You can keep a short shader in a TypeScript string, or keep GLSL and WGSL in dedicated files so shader-aware editors and tools can work with them directly. `@codexo/exojs-build` imports those files as strings; it does not turn a shader into a TypeScript-checked GPU program.

## Configure the build

```sh
npm install --save-dev @codexo/exojs-build
```

The plugin works with the project's supported Vite or Rollup setup:

```ts
import { exojs } from '@codexo/exojs-build';

export default {
  plugins: [exojs()],
};
```

Add its ambient declarations alongside the types your application already uses:

```json
{
  "compilerOptions": {
    "types": ["@codexo/exojs-build/client"]
  }
}
```

Merge this with existing `types` entries rather than deleting the framework or bundler types the project needs. The same plugin also handles the queries described in [Typed worklets and workers](/ExoJS/en/guide/shipping/typed-worklets-and-workers/).

## Keep backend counterparts together

Use `.vert` and `.frag` for GLSL stages and `.wgsl` for WGSL. Import them where the material or filter is created:

```ts
import { ShaderFilter } from '@codexo/exojs';

import fragment from './ripple.frag';
import wgsl from './ripple.wgsl';

const ripple = new ShaderFilter({
  glsl: { fragment },
  wgsl,
  uniforms: { u_time: 0, u_amplitude: 0.02 },
});
```

The imported strings must implement the filter's shader interface and matching uniforms. This fragment shows file organization, not the shader bodies. Use [Filters](/ExoJS/en/guide/effects/filters/) for the filter contract and [Custom mesh shaders](/ExoJS/en/guide/effects/custom-mesh-shaders/) for material attributes, transforms, and uniform schemas.

Providing both languages prevents a missing-backend implementation, but does not prove that the two programs produce the same image. Compile and exercise both paths, including the parameter values and texture formats the application will actually use.

## Know what is validated

TypeScript checks that the import is a string and that the receiving JavaScript API is used correctly. A typed uniform schema can check host-side values and generated declarations. Neither replaces GLSL or WGSL compilation, interface checks, device limits, or visual validation.

Keep shader compilation checks in the build or test pipeline and include a small rendering test for an effect's intended output. A successful application typecheck is not evidence that a GPU accepted the shader.

## Inlining and minification

The plugin inlines source text into the JavaScript bundle; it does not emit a separate shader request. `exojs({ minify: true })` removes supported comments and layout whitespace from that text. It is not an algorithmic shader optimizer and does not make a slow fragment program fast.

A shader assembled dynamically from arbitrary strings does not pass through a file-import transform. Compose and process known source during the build where possible. Do not add build tooling to the application runtime merely to minify a string after the user has already downloaded it.

Bare shader imports are claimed by the plugin. Imports with queries such as `?raw` or `?url` remain the bundler's responsibility, including their TypeScript declarations. Choose a URL import only when a separate runtime resource request is intentional.

## Keep ownership outside the file loader

Importing source does not create a material, attach a filter, or manage GPU lifetime. Construct those objects at the appropriate application or scene boundary, update their parameters without reconstructing them every frame, and release caller-owned resources when that owner ends.

Use the [rendering extension-point guide](/ExoJS/en/guide/debugging/custom-renderers/) when the required work cannot be expressed by a normal material or filter. Changing how source text reaches a shader API does not require a custom renderer.
