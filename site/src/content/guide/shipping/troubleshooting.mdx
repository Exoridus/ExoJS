# Troubleshooting

Start with the first error in the console or failed network request, not the last visible symptom. Reproduce the issue in a minimal scene and compare it with the current Playground. Match the Guide and package versions before copying code: `next` can describe work that an older npm release does not contain.

| Symptom | First checks |
| --- | --- |
| Empty canvas | Await startup; check mounting, size, scene activation, and the draw call. |
| Missing API or unexpected type error | Check installed versions, public import paths, and duplicate Core copies. |
| Missing texture or data | Inspect the actual request URL, response, decoder error, and owner scope. |
| No sound | Check a real user gesture, audio state, bus volume, and voice lifetime. |
| Ignored input | Check focus, scene availability, modal scopes, and the binding. |
| Wrong text or density | Check the loaded font, layout, and logical versus backing size. |
| Stalls or low throughput | Profile the production workload before changing the renderer. |

## Canvas shows nothing

Await `app.start(YourScene)` and surface its rejection. Calling `app.start()` without a target starts the application but does not activate a scene. Register scene classes in `ApplicationOptions.scenes`; do not register preconstructed instances.

Check that the canvas is mounted and that its element and container have nonzero visible dimensions. An application can perform work on a canvas that the page never displays.

The normal scene graph is rendered explicitly:

<SourceSnippet source="examples/guides/troubleshooting/draw-hook.ts" region="draw-root" language="ts" title="Submit the scene root" />

The application clears the frame by default. If `draw` never submits content, a flat clear color is expected. Also check whether the object belongs to the submitted tree, is inside the current view, has usable dimensions, and is hidden by opacity, clipping, or masking. A custom pipeline can submit different roots; do not add a second root draw blindly to a pipeline that already renders it.

The scene's `ui` layer is automatic and separate from `root`. A visible HUD with an empty world is a useful clue that startup succeeded but the world draw or camera is wrong.

## API or lifecycle errors

Inspect the installed dependency tree and use the public package entry points. A package's README states its peers; importing a second Core copy or mismatched runtime packages can break identity-based registration.

Scene-bound services are unavailable in constructors and field initializers. Move `this.app`, `this.loader`, or `this.inputs` access into the appropriate attached lifecycle hook. Await asynchronous prerequisites in `load`; keep `init`, update hooks, and `destroy` synchronous. See [Scenes and lifecycle](/ExoJS/en/guide/runtime/scenes-and-lifecycle/).

A missing method is not a reason to add an old alias to the application. Check the current API reference and release notes for the installed version.

## Assets not loading

Inspect the requested URL in the Network panel. `loader.basePath` and the descriptor path together determine that URL; it is not necessarily relative to the TypeScript file or the page directory you expected.

Files in a Vite project's `public/` directory are served without the `public/` prefix. Do not repeat an `assets/` directory that is already in `basePath`. Check exact filename casing, deployed files, redirects, HTTP status, and cross-origin response headers. A successful HTTP response containing an HTML fallback is not a valid image or JSON asset.

`get()` can return before a resource is ready. Await required resources with `load`, or observe the placeholder's readiness and failure. A loader completion signal means the batch settled, not that every item succeeded. A destroyed scene scope no longer keeps its resources resident.

Use a local HTTP server, not `file://`. For deployment under a subdirectory, follow [Deployment](/ExoJS/en/guide/shipping/deployment/) rather than assuming that Vite rewrites arbitrary strings passed to the loader.

## Audio does not start

Start or unlock audio from an actual click, tap, or supported keyboard gesture. A loaded audio asset is not a playing voice, and a playing voice may still be routed through a muted bus. Inspect both playback and the browser audio context state.

Use the current `AudioSystem` or scene-audio playback API from [Audio basics](/ExoJS/en/guide/audio/audio-basics/). Do not assume a `Sound` asset has a playback method merely because another library used that shape. Repeatedly constructing a sound or retrying playback every frame does not replace a user-gesture boundary.

For a cross-origin stream, verify the server's CORS behavior as well as audibility: analysis and effects may need access that an ordinary media element's playback does not prove.

## Input does not respond

Give the canvas focus and inspect whether another element, modal interaction scope, or scene availability policy owns the input. Scene bindings normally follow active gameplay; a pause toggle must deliberately remain available while paused.

`Keyboard` names physical key positions, not typed characters. Its arrow keys are `Left`, `Up`, `Right`, and `Down`. For text entry and IME composition, use the appropriate text-input widget or DOM input rather than reconstructing text from gameplay channels.

Use action signals for transitions and read held values during the frame loop. A one-time read in `init` cannot track later movement. For a gamepad, press a button to make it visible to the browser, then check connection state and the selected slot. A slot is not a persistent physical-controller identity.

## Text or fonts look wrong

Load the intended font before depending on its metrics. A fallback font can change line breaks and measured bounds. Use the current `TextStyle` properties, including `fillColor`, and distinguish layout bounds from visible ink bounds when aligning text.

Check the canvas sizing policy and pixel ratio. CSS size, logical game coordinates, and backing-store pixels are different quantities. Do not compensate for a DPR issue by multiplying every world position. See [Text](/ExoJS/en/guide/rendering/text/) and [Resize, DPR and the canvas](/ExoJS/en/guide/getting-started/resize-dpr-and-canvas/).

## Backend or performance problems

WebGPU availability depends on the actual browser, device, driver, context, and engine selection policy. Falling back to WebGL2 is not itself a failure. Inspect the selected backend after startup and consult [Backend selection](/ExoJS/en/guide/debugging/backend-comparison/) for measured parity and feature boundaries.

For slow output, separate simulation, submission, pixel work, and memory. A filter is not necessarily one GPU pass, and hiding a node does not automatically stop its game logic. [Debugging and inspection](/ExoJS/en/guide/debugging/debugging-and-inspection/) helps locate the problem; [Performance](/ExoJS/en/guide/debugging/performance/) explains how to measure it.

## Report a reproducible issue

Include the ExoJS and package versions, browser and operating system, selected backend, canvas size and DPR, exact error, and the smallest source that reproduces it. State whether it also occurs in a production build and on the other supported backend. Remove credentials and private assets before sharing the reproduction.
