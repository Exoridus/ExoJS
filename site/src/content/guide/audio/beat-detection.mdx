# Beat detection

The [`BeatDetector`](/ExoJS/en/api/beat-detector/) analyses an audio signal in real time using a self-contained `AudioWorkletProcessor`. It detects tempo, beat positions, and bar/downbeat structure, then reports results back to the main thread as both discrete events (`onBeat`, `onDownbeat`, `onBarStart`, `onTempoChange`) and per-frame polling getters. You use the events for one-shot triggers and the getters for continuous animation — both are covered in detail in [Audio-reactive visualization](/ExoJS/en/guide/audio/audio-reactive-visualization/).

This chapter covers what the detector does and the events it fires. The next chapter covers what you do with that information.

## Connecting a source

The detector taps a live audio source — an `AudioBus`, a `Voice`, an `AudioNode`, or a `MediaStream` — as a parallel branch that does not affect the source's main signal chain. It does not accept a `Sound`/`AudioStream` descriptor; tap the bus the audio plays through (e.g. `app.audio.music`) or the individual `Voice` you got back from `play()`:

```ts
import { type Application, AudioStream } from '@codexo/exojs';
import { BeatDetector } from '@codexo/exojs-audio-fx';

declare const application: Application;
declare const track: AudioStream;

application.audio.play(track, { loop: true });

const detector = new BeatDetector();
detector.source = application.audio.music; // the bus the track plays through
```

You can also pass the source as a constructor option, or point it at a single voice:

```ts
import { type Application, AudioStream } from '@codexo/exojs';
import { BeatDetector } from '@codexo/exojs-audio-fx';

declare const application: Application;
declare const track: AudioStream;

const voice = application.audio.play(track, { loop: true });
const detector = new BeatDetector({ source: voice });
```

The detector runs its own FFT inside the worklet processor. No `AudioAnalyser` is required — `BeatDetector` handles frequency analysis internally. The `fftSize` option (default 2048) and `hopSize` (default 512) control the worklet's internal analysis window.

Assigning a different source, including `null`, clears rhythm history and pending predictions immediately. Assigning the same source again preserves continuity. Call `detector.reset()` after a seek or another playback discontinuity on the same source. The detector cannot infer a track seek, voice pause or EOF from an arbitrary bus. Missing input or a gap in the context-frame stream resets analysis; recorded silence instead remains valid audio and lets predictions expire. `barNumber` remains a lifetime counter across resets. For explicit playback ownership, call `notifyDiscontinuity(reason)` with `seek`, `loop`, `starvation`, `explicitPause`, `resume`, `eof` or `reset`. EOF and explicit pause stop analysis until resume, reset or another source identity. Seek/loop/starvation and manual-context changes preserve an existing stop; recorded silence alone does not end the source.

## Tempo and confidence

Two read-only getters give you the detector's current tempo estimate:

`tempo` returns 0 until the detector has enough data to lock onto a stable beat. `confidence` rises as the beat grid stabilises. The `onTempoChange` signal fires when the detector settles on a new tempo:

```ts
import { BeatDetector } from '@codexo/exojs-audio-fx';

declare const detector: BeatDetector;

detector.onTempoChange.add((newBpm, oldBpm) => {
    console.log(`Tempo changed from ${oldBpm} to ${newBpm} BPM`);
});
```

Beats arrive in two trust levels via `BeatInfo.status`. Early, low-latency beats are tagged `'provisional'` (after a short `minSettlingMs` warm-up, default 400) — ideal for snappy visual reactivity like a beat "blink". Once the tempo grid is settled and trustworthy, beats promote to `'locked'` (each stable segment yields exactly one provisional→locked transition). The single `onBeat` signal carries both; check `info.status` to decide how much to trust a given beat, or set `emitProvisionalBeats: false` to receive only locked beats. The `tempo`/`confidence` getters only report once the grid is locked.

## Event signals

Four signals fire at discrete moments in the music:

| Signal | Fires when | Payload |
|--------|------------|---------|
| `onBeat` | A beat occurs | `BeatInfo` — audio time, tempo, confidence, energy, isDownbeat, meterKnown, beatInBar, status (`'provisional'` \| `'locked'`) |
| `onDownbeat` | The first beat of a bar | Same `BeatInfo` |
| `onBarStart` | A new bar begins | `BarInfo` — audio time, tempo, confidence, barNumber |
| `onTempoChange` | Tempo estimate changes | `(newBpm, oldBpm)` |

Use `onBeat` for things that should happen on every beat — a sprite pulses, a particle burst fires, a UI element flashes:

```ts
import { BeatDetector } from '@codexo/exojs-audio-fx';

declare const detector: BeatDetector;
declare const particleBurst: { reset(): void };
const visualState = { pulse: 0 };

detector.onBeat.add(info => {
    visualState.pulse = 0.3;
    particleBurst.reset();
});
```

<Callout type="pitfall" title="Beat signals are not frame-locked">
`onBeat` and its siblings fire from the worklet as it detects each beat, delivered asynchronously to the main thread — not aligned to your `update` frame, and possibly finer than `requestAnimationFrame`. Use them for one-shot triggers; for visuals that must stay frame-stable, poll getters like `pulse` or `justBeat` in `update` instead.
</Callout>

Use `onDownbeat` for events that should only fire on the "one" — a brighter flash, a bar-level visual change, a camera shake:

```ts
import { BeatDetector } from '@codexo/exojs-audio-fx';

declare const detector: BeatDetector;
const visualState = { barFlash: 0 };

detector.onDownbeat.add(info => {
    visualState.barFlash = 0.5;
});
```

`BeatInfo` carries `isDownbeat` and `beatInBar` so you can use the general `onBeat` signal and filter inside the callback:

```ts
import { BeatDetector } from '@codexo/exojs-audio-fx';

declare const detector: BeatDetector;

detector.onBeat.add(info => {
    if (info.isDownbeat) {
        // big effect on beat 1
    } else if (info.meterKnown && info.beatInBar === 3) {
        // secondary emphasis on beat 3
    }
});
```

## State getters

The detector exposes read-only state you can poll every frame:

```ts
import { BeatDetector } from '@codexo/exojs-audio-fx';

declare const detector: BeatDetector;

detector.tempo              // BPM, or 0 before lock
detector.confidence         // 0..1 locking quality
detector.beatPhase          // 0..1 phase within current beat
detector.barPosition        // display counting; check meterKnown for bar phase
detector.barLength          // beats per bar (default 4)
detector.timeSignature      // legacy display convention, denominator 4
detector.meterEstimate      // interpretation view; selected can be null
detector.meterKnown         // current cycle and phase available
detector.rms                // 0..1 overall RMS energy
detector.onsetStrength      // 0..1 onset novelty at current frame
detector.bandEnergy         // { low, mid, high } band energies
detector.tempoCandidates    // readonly array of { bpm, score } candidates
detector.lookahead          // readonly array of upcoming beats
```

These are pure derivations from the detector's most recent worklet state update — no allocation, no event dispatch.

Predictions additionally check the current audio-context time. `predictionValidUntil` reports when a retained schedule must be discarded, or 0 when unavailable. Without renewed onset support, this is two tracked beat periods plus one FFT window. After expiry, `lookahead` returns an empty array and `nextBeatTime` / `nextDownbeatTime` return 0. The next-time getters skip past entries; a retained `lookahead` array can still contain them. Later extrapolated times are conditional on the rhythm continuing. `onBeatPredicted` announces each received revision at most once, skips expired schedules, and does not coalesce distinct revisions queued for delivery.

`minSettlingMs` bounds the first beat's posting time, rounded up to an analysis hop. A beat posted after warm-up can carry an earlier onset timestamp. `BeatInfo.energy` is raw novelty from the hop that emitted the beat, rather than a normalized score or necessarily the matched onset's energy. `onsetEnergy` and `onsetAudioTime` separately identify the matched onset, or are null without a match. `beatConfidence` omits the legacy meter factor; `confidence` retains it for compatibility with lock behavior. These are uncalibrated scores, and `gridStability` remains a legacy alias of `confidence`. Cached rhythm getters return unavailable values once their prediction validity expires, including when the worklet sends no new state.

<Callout type="info" title="Trust tempo and confidence only once locked">
Beats arrive `'provisional'` first — low-latency and ideal for snappy visual reactivity — then promote to `'locked'` once the grid settles, and `tempo`/`confidence` read 0 until that point. Gate anything that needs a dependable BPM — a sequencer, a UI readout — on `info.status === 'locked'`.
</Callout>

## Bar and time-signature tracking

With `enableTimeSignatureDetection: true` (the default), the detector compares three- and four-pulse accent cycles on the same matched onset observations, using finalized attack power. Meter stays unknown until enough observations favor a cycle and phase over the alternatives. Beats continue during acquisition and ambiguity, with `meterKnown: false` and `isDownbeat: false`; no automatic `onDownbeat` or `onBarStart` events fire then.

`meterEstimate` is an immutable view with `selected`, up to two distinct `alternatives`, `score`, `reason`, `origin`, `evidenceThroughAudioTime` and `validUntilAudioTime`. Its selected model contains `cyclePulses`, `pulsePeriodSeconds`, zero-based `phasePulses` and `denominator`. A null selection means the cycle is unknown; a null phase means that cycle has no identified bar anchor. `meterKnown` requires both. Reasons distinguish acquisition, insufficient observations, low contrast, cycle ambiguity, phase ambiguity, availability and expiry. Scores are not probabilities, and the automatic denominator remains null.

The times use the audio-context clock. A current interpretation can expire before the beat schedule: `nextDownbeatTime` and `barPulse` then return 0 and `lookahead` keeps beat times while clearing downbeat flags. Finalized evidence may revise a schedule without a new beat; handle every new `onBeatPredicted` revision. The separate `schedule` view records epoch, revision, generation/evidence times, validity, conditional horizon, tracked pulse period and trust status at generation. It returns null after invalidation. Its `nextBeat` and `nextDownbeat` are future entries or null. A retained schedule with downbeat flags expires with the meter; fetching a new view can retain beat-only predictions for the remaining pulse deadline.

Set detection `false` for an explicit four-beat counting convention, anchored to the first tracked beat rather than an inferred musical bar. Its estimate has `origin: 'convention'` and score 1, which describes the chosen rule rather than certainty about the music:

```ts
import { BeatDetector } from '@codexo/exojs-audio-fx';

const detector = new BeatDetector({
    enableTimeSignatureDetection: false,
});
```

`barPosition` (1-based), `barLength` and `timeSignature` remain legacy display values even while `meterEstimate.selected` is null; check `meterKnown` before treating them as bar information. `cyclePulses` counts the detector's tempo-grid pulses, not notated beats, and the default legacy denominator 4 is a display convention. Automatic discrimination and phase are not independently qualified on a representative music corpus. A locked beat grid does not establish a correct downbeat. Use an independently authored timeline when gameplay or a sequencer requires authoritative bars.

When migrating existing callers, allow missing automatic bar events during acquisition or ambiguity. Use `onBeat` for continuous beat-level visuals and gate bar-dependent behavior on `meterKnown`; callers intentionally counting every four beats can select the fixed convention above.

Provide explicit context when the intended cycle is already known:

```ts
import { BeatDetector } from '@codexo/exojs-audio-fx';

declare const detector: BeatDetector;

detector.manualMeter = { cyclePulses: 3, phasePulses: 0, denominator: 4 };
// The next epoch anchors phase 0 to its first tracked beat.
detector.manualMeter = { cyclePulses: 3 }; // known cycle, unknown phase
// Return to automatic interpretation.
detector.manualMeter = null;
```

The origin is `manual`, so this does not claim an acoustic downbeat. Integers from 1 through 32 are accepted as cycle lengths; phase must be within that cycle, and an optional denominator must be a power of two from 1 through 128. Invalid values throw before changing analysis. The setter snapshots its input; changing context resets history and predictions. Source changes and `reset()` preserve configuration but establish a new phase anchor. Reapplying identical context preserves continuity. With a long cycle, the next downbeat may lie outside the eight-entry forecast and return 0 while a valid `barPulse` can still describe the last boundary.


## Worklet processor

`BeatDetector` uses an `AudioWorkletProcessor` that runs entirely in the Web Audio rendering thread. It applies a Hann window, runs a radix-2 FFT, computes mel-band energies, detects onsets via spectral flux, builds a tempogram with autocorrelation, and tracks beat phase with a bounded phase-locked loop (PLL). All of this is internal — the public API is the events and getters listed above.

Beat/state messages are posted from the worklet and handled asynchronously on the main thread. They are not locked to your scene's `update` timing, and worklet timing can be finer than `requestAnimationFrame`. For frame-stable visual animation, prefer polling getters in `update` (see [Audio-reactive visualization](/ExoJS/en/guide/audio/audio-reactive-visualization/)).

## Configuring the detector

Construction options with their defaults:

```ts
import type { Application } from '@codexo/exojs';
import { BeatDetector } from '@codexo/exojs-audio-fx';

declare const application: Application;

const detector = new BeatDetector({
    minBpm: 50,                            // minimum detectable tempo
    maxBpm: 300,                           // maximum detectable tempo
    fftSize: 2048,                         // internal FFT window
    hopSize: 512,                          // samples between successive FFTs
    fastTempoWindowSec: 2.5,               // short tempogram window (reacts to tempo changes)
    stableTempoWindowSec: 8,               // long tempogram window (holds the grid steady)
    acfIntervalHops: 15,                   // hops between tempogram recomputations
    minSettlingMs: 400,                    // warm-up before the first (provisional) beat
    emitProvisionalBeats: true,            // emit early provisional beats for visual reactivity
    melBands: 24,                          // mel filterbank bands
    enableTimeSignatureDetection: true,    // estimate a three-/four-pulse cycle, otherwise unknown
    source: application.audio.music,       // initial source: bus or Voice (optional)
});
```

`minBpm` and `maxBpm` constrain the tempo search. The tempogram runs two autocorrelation windows: `stableTempoWindowSec` holds a steady tempo grid, while the shorter `fastTempoWindowSec` reacts to tempo changes — the tracked tempo only follows the fast window when it disagrees with the stable one consistently, so a real DJ drift is tracked without making a steady tempo nervous. `acfIntervalHops` sets how often the tempogram is recomputed (lower reacts faster at more CPU). `melBands` controls the granularity of the internal onset detection; the default of 24 is sufficient for most music.
