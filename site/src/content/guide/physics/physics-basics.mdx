# Physics and scene ownership

Use `@codexo/exojs-physics` when gameplay needs rigid bodies, contact response, joints, or queries against a simulated world. For a pointer hit test or a few geometric overlap checks, [Gameplay collision](/ExoJS/en/guide/recipes/gameplay-collision/) may be sufficient.

The physics package is a library and a system, not an application extension descriptor. Install it alongside Core, construct a `PhysicsWorld`, and give that world an owner. There is no physics registration import to activate globally.

```sh
npm install --save-exact @codexo/exojs @codexo/exojs-physics
```

`this.systems.add(world, ...)` lets the scene's system registry drive and destroy the world. `world.attach` creates a body and collider and binds the node to the simulated transform. The scene root owns the visible graphics. Those are separate ownership relationships even though one helper connects them.

Do not also call `world.step()` from `update` or `fixedUpdate` in this setup. A second call would step the same world twice.

## Choose one clock

For an ordinary ExoJS scene, register the world as a scene system with `SystemOrder.Physics`. The host supplies its fixed-step phase. Use scene updates for gameplay decisions and let the system update the simulated state.

An independently hosted world can instead be driven manually with `world.step(frameDeltaSeconds)`. That API owns an accumulator and advances its configured fixed steps. It is useful outside a scene or when a host deliberately manages the world itself. Do not combine manual stepping with automatic system registration.

A constant timestep controls integration intervals; it does not guarantee cross-machine lockstep or rollback determinism. Long stalls, catch-up limits, input timing, and floating-point behavior still matter. Test the actual simulation and record its inputs when reproducibility matters.

## Bodies, colliders, and drawing

A body carries simulated transform and motion. A collider supplies geometry, material properties, filtering, and optional sensor behavior. A rendered node supplies the image. Changing a sprite's art does not automatically redefine an independently created collider.

| Body type | Typical use |
| --- | --- |
| Static | Floors, walls, and fixed level geometry. |
| Dynamic | Objects moved by forces, impulses, gravity, and contact response. |
| Kinematic | Motion controlled by your code while still participating in collision rules. |

Solid shapes such as boxes, circles, capsules, and convex polygons enclose area and contribute to the mass model. Segments and chains are boundary geometry. A dynamic body needs suitable solid geometry; a chain alone is not a solid mass. Use the polygon-conversion helper for a concave outline instead of passing arbitrary concave vertices to a convex shape.

Keep the visual node's origin aligned with the collider's intended origin. The example draws each rectangle around `(0, 0)` and lets the binding place it. Moving a bound node directly fights the physics result; change the body or the control that drives it instead.

## Bodies as components

`PhysicsBodyComponent` ties a body's place in the world to its node. The body joins the world when the node becomes active in a scene and leaves it, keeping its position, velocity and colliders, whenever the component is disabled, the node is removed or reparented, or the scene is retained. It comes back on the next activation. Destroying the node destroys the body, so a removed enemy no longer leaves an invisible collider behind. Pausing the scene changes nothing here: a world registered as the scene's system stops stepping with it, while a world owned elsewhere keeps running.

<SourceSnippet source="examples/guides/physics-basics/body-component.ts" region="body-component" language="ts" title="Bodies owned by their nodes" />

Pass the world explicitly; the component never looks one up. Without a `position`, the body starts at the node's world position. `scene.query(PhysicsBodyComponent)` lists every node that carries one, including disabled components whose bodies are out of the world, and `node.getComponent(PhysicsBodyComponent)?.body` reaches the body from gameplay code.

A component-managed body cannot take part in a joint yet, mouse joints included. Use `world.add` and `world.bind` for bodies that need joints. `world.attach`, `world.add` and `world.bind` remain available whenever you want to manage a body's lifetime yourself, and `world.remove(body)` takes a body out of the simulation without destroying it.

## Coordinates, units, and rotation

The world uses the coordinate units you choose. In a pixel-based scene, velocity is pixels per second and gravity is pixels per second squared. Scale your level and physical parameters consistently rather than mixing meters with unconverted pixel coordinates.

Positions use the scene's y-down convention, but rotation interfaces differ: physics angles are **radians**, with positive rotation clockwise on screen; scene-node rotation is **degrees**, with positive rotation counterclockwise on screen. The built-in node binding converts both the unit and sign. A manual binding needs the same conversion, not just multiplication by `180 / Math.PI`.

The normal workflow is to use `bind` or `attach` instead of copying transforms yourself. Test unusual parent transforms and offsets deliberately; a body's world transform is not interchangeable with a node's local transform under an arbitrary parent.

## Smooth presentation without changing simulation

Physics runs at fixed intervals, while rendering can happen between them. The world supports interpolation of bound-node presentation. Its alpha must come from the clock that actually drives that world: a manually accumulated world and a host-fixed-step world do not necessarily have the same remainder.

Use the world's interpolation configuration and frame-alpha source described in the [`PhysicsWorld` reference](/ExoJS/en/api/physics-world/). Interpolation blends previous and current simulated state for display; it does not create additional collision steps. Teleports should use the body's transform API so presentation history does not drag the object through an unintended path.

## Sensors, contacts, and queries

Use sensors for regions that report overlap without physical response. Use collision events for gameplay reactions to contact boundaries, and spatial queries for explicit questions such as what lies under a cursor or along a ray. Avoid treating an event as permission to mutate an event object or retain a borrowed contact record indefinitely; the relevant API states whether it is a snapshot or callback-scoped data.

A contact modifier changes contact policy, not the existence of the entire gameplay event system. For one-way platforms or conditional material behavior, see [Joints and contact behavior](/ExoJS/en/guide/physics/joints-and-dynamics/).

## Level geometry and teardown

`@codexo/exojs-tilemap-physics` connects authored tile geometry to static bodies and streamed chunk lifetimes. Rendering a tilemap does not automatically create collision. Keep the physics bridge synchronized before the corresponding simulation step and release streamed colliders with their level owner.

When the scene ends, its system registry destroys the registered world and its scene graph destroys the visible nodes. External listeners, application-owned worlds, or raw references retained by another subsystem still need their own lifetime decision. Do not keep a scene-owned body as a valid gameplay handle after its world has ended.
