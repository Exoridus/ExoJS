# Physics and scene ownership

Use `@codexo/exojs/physics` when gameplay needs rigid bodies, contact response, joints, or queries against a simulated world. For a pointer hit test or a few geometric overlap checks, [Gameplay collision](/ExoJS/en/guide/recipes/gameplay-collision/) may be sufficient.

The physics package is a library and a system, not an application extension descriptor. It ships inside Core; construct a `PhysicsWorld`, and give that world an owner. There is no physics registration import to activate globally.

```sh
npm install --save-exact @codexo/exojs
```

## Choose one clock

For an ordinary ExoJS scene, register the world as a scene system with `SystemOrder.Physics` and build it with `fixedDelta: this.app.fixedTimeStep`. The world then steps exactly once per application fixed step, after the scene's `fixedUpdate` and its behaviours, so a command they issue in a step is applied by that step. A registered world simulates its own `fixedDelta` on every host step, so the two must agree: a world whose `fixedDelta` differs from the host step throws on its first step, before anything moves, instead of running too fast or too slow. Read discrete input for such commands through an action's `tick` view, which hands each press to exactly one fixed step.

A world can instead be driven manually with `world.step(frameDeltaSeconds)`. That API owns an accumulator and advances its configured fixed steps, at any rate, up to its `maxSubSteps` per call. It is useful outside a scene or when a host deliberately manages the world itself. Choose one stepping clock. Development builds report mixing hosted and manual steps. A world can have one system registry at a time. Remove it from its current registry before registering it elsewhere.

A world registered in `app.systems` instead of the scene's is an advanced setup with different scheduling: it steps before any scene code in each fixed step, so a scene command reaches it one step later, and it keeps stepping while the scene is paused.

A constant timestep controls integration intervals; it does not guarantee cross-machine lockstep or rollback determinism. Long stalls, catch-up limits, input timing, and floating-point behavior still matter. Test the actual simulation and record its inputs when reproducibility matters.

## Bodies, colliders, and drawing

A body carries simulated transform and motion. A collider supplies geometry, material properties, filtering, and optional sensor behavior. A rendered node supplies the image. Changing a sprite's art does not automatically redefine an independently created collider.

| Body type | Typical use |
| --- | --- |
| Static | Floors, walls, and fixed level geometry. |
| Dynamic | Objects moved by forces, impulses, gravity, and contact response. |
| Kinematic | Motion controlled by your code while still participating in collision rules. |

Solid shapes such as boxes, circles, capsules, and convex polygons enclose area and contribute to the mass model. Segments and chains are boundary geometry. A dynamic body needs suitable solid geometry; a chain alone is not a solid mass. Use the polygon-conversion helper for a concave outline instead of passing arbitrary concave vertices to a convex shape.

Keep the visual node's origin aligned with the collider's intended origin. The example draws each rectangle around `(0, 0)` and lets the binding place it. Moving a bound node directly fights the physics result; change the body or the control that drives it instead.

## Bodies as components

`PhysicsBodyComponent` ties a body's place in the world to its node. The body joins the world when the node becomes active in a scene and leaves it, keeping its position, velocity and colliders, whenever the component is disabled, the node is removed from its scene, or the scene is retained. Moving the node to another parent of the same scene is not a disable: the body stays in the world. After a disable it comes back on the next activation. Destroying the node destroys the body, so a removed enemy no longer leaves an invisible collider behind. Pausing the scene changes nothing here: a world registered as the scene's system stops stepping with it, while a world owned elsewhere keeps running.

<SourceSnippet source="examples/guides/physics-basics/body-component.ts" region="body-component" language="ts" title="Bodies owned by their nodes" />

The options-only constructor selects the scene's sole live `PhysicsWorld` on first activation. Register it before activation and include the fixed-step phase. A missing or ambiguous world is reported through the scene's error handler. Pass `new PhysicsBodyComponent(world, options)` to select a particular world or use an app-owned or manually stepped world. The component keeps its first world across reactivation. Removing an inferred world from the registry disables its automatically bound components at the detach boundary. To activate again, register that same world and enable the component. To use a different world, replace the component and explicitly initialize the destination body.

Without a `position`, the body starts at the node's world position pivot: its origin transformed by the full world matrix. An anchor therefore does not shift the body to the image's top-left corner. An explicit body position takes precedence. `scene.query(PhysicsBodyComponent)` lists every node that carries one, including disabled components whose bodies are out of the world, and `node.getComponent(PhysicsBodyComponent)?.body` reaches the body from gameplay code.

Destroying a world destroys its attached bodies, releases movement controllers and clears their components' `activeWorld`. Replace a component whose body was destroyed to resume simulation.

A component-managed body cannot take part in a joint yet, mouse joints included. Use `world.add` and `world.bind` for bodies that need joints. `world.attach`, `world.add` and `world.bind` remain available whenever you want to manage a body's lifetime yourself, and `world.remove(body)` takes a body out of the simulation without destroying it.

| Binding choice | What it creates/owns | When the node ends |
| --- | --- | --- |
| `world.attach(node, definition)` | Creates a world-owned body and collider, and a body-to-node binding. | The link is removed; the body stays in the world until explicitly removed/destroyed or the world ends. |
| `world.add(body)` then `world.bind(body, node)` | The caller constructs the body; the world owns its simulation membership and binding. | Ending the binding does not destroy the body. This is the path for jointed bodies. |
| `node.addComponent(new PhysicsBodyComponent(options))` | The component owns the body and couples membership to enable/disable. | Destroying the node/component destroys the body; disable preserves it for reactivation. |

Choose one binding path per node. `world.remove(body)` removes membership without destroying a manually managed body. Component-managed membership belongs to the component, so do not separately add/remove that body.

## Coordinates, units, and rotation

The world uses the coordinate units you choose. In a pixel-based scene, velocity is pixels per second and gravity is pixels per second squared. Scale your level and physical parameters consistently rather than mixing meters with unconverted pixel coordinates.

Positions use the scene's y-down convention, but rotation interfaces differ: physics angles are **radians**, with positive rotation clockwise on screen; scene-node rotation is **degrees**, with positive rotation counterclockwise on screen. The built-in node binding converts both the unit and sign. A manual binding needs the same conversion, not just multiplication by `180 / Math.PI`.

Use a component, `bind`, or `attach` to let the body drive the node's displayed position and rotation. Translated and rotated parents, including retained groups, are supported. A parent whose composed world transform contains scale, reflection or shear, or a node with skew or nonpositive scale, is rejected on bind. If an unsupported transform is introduced later, the world keeps simulating and the binding logs a diagnostic and skips pose writes until the transform is repaired. Bind a node to one body and keep physics-driven ancestors in the same world so their display poses are updated first.

`Collider.boxFromBounds(node)` takes one snapshot of local bounds, local scale and origin. It produces a box centered relative to the node's pivot. For a circle, specify the radius with `new CircleShape(radius)` and supply a body-local `offset` when the shape is off-center. Use explicit geometry for padded or irregular art. Several colliders can share one body; all offsets use the same body-local coordinates. Build a new collider when bounds, anchor or scale changes should affect physics.

## Smooth presentation without changing simulation

Physics runs at fixed intervals, while rendering can happen between them. The world supports interpolation of bound-node presentation. Its alpha must come from the clock that actually drives that world: a manually stepped world uses its own accumulator by default, while a registered world needs the host's, `frameAlphaSource: () => this.app.frameAlpha`. Without one, a registered world presents its latest step unsmoothed and development builds warn.

Use the world's interpolation configuration and frame-alpha source described in the [`PhysicsWorld` reference](/ExoJS/en/api/physics-world/). Interpolation blends previous and current simulated state for display; it does not create additional collision steps. Teleports should use the body's transform API so presentation history does not drag the object through an unintended path.

## Sensors, contacts, and queries

Use sensors for regions that report overlap without physical response. Use collision events for gameplay reactions to contact boundaries, and spatial queries for explicit questions such as what lies under a cursor or along a ray. Avoid treating an event as permission to mutate an event object or retain a borrowed contact record indefinitely; the relevant API states whether it is a snapshot or callback-scoped data.

A contact modifier changes contact policy, not the existence of the entire gameplay event system. For one-way platforms or conditional material behavior, see [Joints and contact behavior](/ExoJS/en/guide/physics/joints-and-dynamics/).

### Collision filters

| Field | Default | Rule |
| --- | --- | --- |
| `category` | `0x0001` | Bits describing this collider. |
| `mask` | `0xffff` | Categories this collider accepts; the default covers the low 16 bits. |
| `group` | `0` | Equal positive groups override the masks to permit a pair; equal negative groups reject it. Zero or unequal groups use the mask rule. |
| `isSensor` | `false` | A sensor reports overlap without contact impulses. |

With no equal nonzero group override, both `(a.mask & b.category) !== 0` and `(b.mask & a.category) !== 0` must hold. Use project constants such as `const Layer = { player: 1 << 0, enemy: 1 << 1, world: 1 << 2 } as const`; no string-layer registry is needed. See [the enemy sensor recipe](/ExoJS/en/guide/recipes/gameplay-collision/#enemies-and-physics-sensors) for both sides of the filter and a single collider-to-gameplay dispatcher.

Events describe collider pairs. A multi-collider player may need a per-body overlap count or another explicit deduplication rule. Removing a collider produces its exit on a subsequent step, but destroying the world is not a guaranteed final stream of exit callbacks. Remove gameplay state at its ownership boundary rather than waiting for one last exit event.

### Query contracts

Omitting a query filter accepts every category. Passing a partial filter, including only `{ mask }`, fills missing fields with the collider defaults and applies the same **mutual** filter rule; it is not a one-sided layer scan. Ordinary point, AABB, ray, and overlap queries can return sensors. `shapeCast` excludes them by default.

| Question | API | Results and boundaries |
| --- | --- | --- |
| What contains this world point? | `queryPoint(point, filter?)` | Fresh collider array. |
| Which AABBs overlap a world region? | `queryAabb(bounds, filter?, out?)` | Reuses/clears an optional output array; candidates are not an exact shape-overlap result. |
| Can I visit those candidates without an array? | `forEachAabbHit(bounds, filter, callback)` | Reuses scratch storage; the callback must not recursively call this method on the same world. Other query methods use separate buffers. |
| What exactly overlaps this shape? | `overlapShape(shape, position, filter?, angle?)` | Fresh collider array; angle is radians. |
| What lies along a line of sight? | `rayCast` / `rayCastAll` | A finite nonzero direction is normalized internally. `maxDistance` is in world units; rays ignore solid shapes containing the origin. `rayCastAll` can reuse an output array and sorts by distance. |
| What blocks a translation? | `shapeCast(shape, position, displacement, options?, out?)` | First hit or null; translation only, with optional output hit, self-exclusion, filter, and `includeSensors`. It is not a rotating sweep. |

Shape casts reject segment/chain inputs because those do not enclose area. They can report an initial overlap at fraction zero; movement out of an overlap or along its surface is treated separately. Reuse output buffers only after finishing the consumer of the previous result. See the [`PhysicsWorld` reference](/ExoJS/en/api/physics-world/) for the exact argument order and hit fields.

## Level geometry and teardown

`@codexo/exojs/tilemap-physics` connects authored tile geometry to static bodies and streamed chunk lifetimes. Rendering a tilemap does not automatically create collision. Keep the physics bridge synchronized before the corresponding simulation step and release streamed colliders with their level owner.

When the scene ends, its system registry destroys the registered world and its scene graph destroys the visible nodes. External listeners, application-owned worlds, or raw references retained by another subsystem still need their own lifetime decision. Do not keep a scene-owned body as a valid gameplay handle after its world has ended.
