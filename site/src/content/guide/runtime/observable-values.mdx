# Observable values

Game state changes at specific moments: a hit lowers health, a pickup adds ammo, a node moves. An observable value reports those moments to whoever subscribed, so nothing has to poll every frame.

- `Observable<T>` holds one value of any type. `Observable.struct()` groups several of them, and `Observable.batch()` delivers several changes as one.
- `ObservableVector` and `ObservableSize`, which nodes already use for `position`, `scale` and similar properties, can be observed too.

All of them share one small contract, `ReadonlyObservable<T>`: a `value`, a `subscribe` method, and `map` for derived values. There is no proxy, no hidden dependency tracking and no per-frame work.

## Observable

```ts
import { Observable } from '@codexo/exojs';

const health = new Observable(100);
const name = new Observable('Hero');

const stop = health.subscribe(value => console.log(`health is now ${value}`));

health.value -= 10; // logs "health is now 90"
health.value = 90; // equal value: nothing happens
name.value = 'Knight';

stop();
```

The type is inferred from the initial value, or given explicitly: `new Observable<Enemy | null>(null)`. Assigning `value` notifies only when the new value differs (`Object.is`), so repeated equal assignments are a cheap comparison. Assigning a number or string allocates nothing.

An object changed in place keeps its identity, so assigning it again notifies nothing. Say so explicitly:

```ts
import { Observable } from '@codexo/exojs';

const inventory = new Observable<string[]>([]);

inventory.mutate(items => items.push('sword')); // changes and notifies once
inventory.value.push('shield');
inventory.markChanged(); // notifies after a change made elsewhere
```

`subscribe` returns the function that ends the subscription; calling it twice is harmless. `destroy()` removes every subscriber at once.

## Derived values

`map` derives a read-only value:

```ts
import { Observable } from '@codexo/exojs';

const health = new Observable(100);
const status = health.map(hp => (hp > 50 ? 'Healthy' : 'Wounded'));

status.subscribe(text => console.log(text));

health.value = 90; // status is still 'Healthy': nothing is logged
health.value = 40; // logs 'Wounded'
```

A derived value is lazy. It subscribes to its source only while it has subscribers itself, so a derived value nobody observes costs nothing and is garbage-collected normally. Reading its `value` always returns the current result: it is computed on demand and reused until something it depends on changes. Over writable observables, a change computes each affected derived value at most once, also along chains and when several derived values share a source, and never from a mix of old and new values. Vectors, sizes and observables from outside the engine cannot report changes while nobody observes them, so a value derived from one is recomputed on every read while it has no subscribers; once subscribed, it computes once per change like any other. A projection must therefore depend only on its sources, never on other state. A derived value notifies only when the result changes, except for newly computed objects, which may have changed in place and therefore always notify.

## Structs

`Observable.struct()` turns each member of a plain object into its own observable:

```ts
import { Observable } from '@codexo/exojs';

const player = Observable.struct({
  name: 'Hero',
  health: 100,
  stats: Observable.struct({ ammo: 30, level: 1 }),
});

player.health.value -= 10;
player.stats.ammo.value--;

const summary = player.health.map(hp => `${hp} HP`);
```

Member types are inferred exactly: `player.health` is an `Observable<number>` and `player.stats.ammo` too. A member that already is an observable, a derived value, a vector, a size or another struct is kept as it is, so several structs can share it. Nothing is traversed: an ordinary nested object or array becomes the value of one observable, and changes inside it are not reported. Nest structs explicitly where you want observable members further down. The object you pass in is not modified, and the struct is frozen.

A struct owns nothing and needs no teardown. The observables it created belong to whoever holds the struct and are collected with it. A shared observable stays owned by its creator; destroying it affects every struct that holds it.

## Batches

`Observable.batch()` groups several changes into one notification:

```ts
import { live, Observable } from '@codexo/exojs';

const player = Observable.struct({ health: 40, stats: Observable.struct({ ammo: 3, level: 1 }) });
const hud = live`HP: ${player.health} | Ammo: ${player.stats.ammo}`;

hud.subscribe(text => console.log(text));

Observable.batch(() => {
  player.health.value = 100;
  player.stats.ammo.value = 30;
  player.stats.level.value++;
}); // logs "HP: 100 | Ammo: 30" once
```

Writes take effect immediately, so code inside the batch reads the new values, and derived values compute from them. Subscribers are notified once the outermost batch completes: values in the order they first changed, and each derived value after everything it depends on. A derived value recomputes once and notifies only if its result changed. The text above is therefore computed and applied once, and no subscriber ever sees a mix of old and new values.

- **Nesting**: inner batches only add to the outer one.
- **Listener changes**: changes made by listeners while the batch is delivered are delivered in the same pass, after the current ones.
- **No rollback**: when the callback throws, the writes made so far stay, their notifications are delivered, and the error is rethrown. A listener that throws stops the remaining listeners of that value, as outside a batch, but every other queued value is still delivered and the first error is rethrown.
- **Synchronous only**: a callback that returns a promise is rejected, because writes after an `await` would not be batched.
- **Vectors and sizes**: their owners, such as a node's transform, are still invalidated at once; only subscribers wait for the batch.

Outside a batch, every change notifies immediately.

## Observing vectors and sizes

A node's `position`, `scale` and other observable vectors implement the same contract. The value is the vector itself, which keeps its identity while it moves, so each change notifies:

```ts
import { Sprite } from '@codexo/exojs';

const player = new Sprite(null);
const readout = player.position.map(p => `${p.x.toFixed(1)} | ${p.y.toFixed(1)}`);
const stop = readout.subscribe(text => console.log(text));

player.position.x += 10;
player.position.set(100, 200);

stop();
```

Observation costs nothing until the first subscription: an unobserved vector has no extra field, closure or allocation, and its owner is notified exactly as before. Subscribers run after the owner, so a node's transform is already invalidated when they see the change.

## Live text

The `live` tagged template builds text from observable values:

```ts
import { live, Observable, Sprite } from '@codexo/exojs';

const health = new Observable(100);
const ammo = new Observable(30);
const player = new Sprite(null);

const title = live`Health: ${health}`;
const ammunition = live`Ammo: ${ammo} / 30`;
const position = live`Position: ${player.position}`; // "Position: 0, 0"

title.subscribe(text => console.log(text));
health.value = 75; // logs "Health: 75"
```

Observable substitutions are read each time the text is computed. Every other substitution is converted once, like in an ordinary template literal, and a template without observable substitutions returns a plain `string`. Functions and promises are rejected, because they would never be read again. An ordinary template literal, or a plain property read such as `player.x`, is always a snapshot.

Vectors print as `120, 80`, sizes as `1920 × 1080` and rectangles as `10, 20, 200, 100`, without rounding. Format numbers yourself in `map`, as in the readout above.

## Binding properties

`bindProperty(target, key, source)` writes an observable's value to an ordinary property, now and after every change, through the property's own setter. The property keeps its ordinary type: `label.text` stays a string and `button.visible` a boolean. Nothing polls, and no scene-wide binding system exists.

- **Initial value**: applied immediately.
- **Types**: TypeScript accepts only writable, non-function properties and a source of the property's type. For a property of type `string` it also accepts a number source, which the binding converts with `String`. Nullable strings and restricted string types such as `'left' | 'right'` accept sources of their own type only, so `null` stays `null`; convert numbers for them explicitly with `map`.
- **Redundant writes**: a derived source notifies only when its result changes, so an unchanged result never reaches the setter. An observed object that changes in place, such as a vector, is written again on every change.
- **Manual writes**: a value you assign directly stays until the source changes again. The binding does not watch the property.
- **Lifetime**: `bindProperty` returns the function that removes the binding. A binding on a scene node also ends when the node is destroyed, including through its parent or its scene, so a destroyed node never keeps a subscription. A retained, inactive scene keeps its bindings and stays current while it is not shown. A binding on any other object lasts until you unbind it.

## Order and reentrancy

Subscribers run in the order they subscribed. A subscriber that changes the value it is observing does not interrupt the notification in progress: the remaining subscribers receive the value of that round first, then every subscriber receives the new value. Subscribers therefore never see values out of order, and the last value each one receives is the current one. A cycle that keeps changing the value is stopped with an error after 100 rounds. A subscriber that throws stops the remaining subscribers of that notification, and the error reaches the code that made the change.
