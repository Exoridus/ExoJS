# JSX construction

JSX is another way to write the constructors you already use. `<Button label="Continue" onClick={resume} />` calls `new Button({ label: 'Continue' })` and adds `resume` to `button.onClick`. The tag returns that button. Nothing else is involved: there is no virtual DOM, no reconciliation, no re-rendering, no hooks, and no per-frame work. After construction, a node built with JSX is indistinguishable from one built with `new`. The renderer, layout, input, lifecycle and ownership rules stay exactly as they are.

## Setup

JSX is optional. The compiler pulls in the runtime only for files that use it, so code without `.tsx` files ships none of it. Point TypeScript's automatic JSX transform at ExoJS:

```json
{
  "compilerOptions": {
    "jsx": "react-jsx",
    "jsxImportSource": "@codexo/exojs"
  }
}
```

Projects scaffolded by `create-exo-app` already have these two options. Vite reads them from `tsconfig.json` and needs no plugin. The compiler imports `@codexo/exojs/jsx-runtime` (`@codexo/exojs/jsx-dev-runtime` in development builds). Type-only helpers for your own element functions and classes come from `@codexo/exojs/jsx`.

## A menu

<SourceSnippet source="examples/guides/jsx/pause-menu.tsx" region="pause-menu" language="tsx" title="examples/guides/jsx/pause-menu.tsx" />

Each tag maps to one constructor call:

- **Constructor options.** Props that are not node properties or handlers go to the constructor as its options object: `width`, `label` and `spacing` above. Classes whose constructor takes positional arguments ship an adapter: `<Sprite texture>`, `<Text text>`, `<Label text style>`, `<NineSliceSprite texture>`, `<RepeatingSprite texture>`, `<AnimatedSprite texture clips>`, `<BitmapText text font fontScale>` and `<HTMLText html>`. Node property names (below) and `on*` names are reserved: JSX assigns them through setters or treats them as signal handlers, so they never reach a constructor. A class whose options use such a name is rejected at compile time until an adapter renames the prop.
- **Node properties.** `name`, `x`, `y`, `rotation`, `scale`, `origin`, `skewX`, `skewY`, `visible`, `zIndex`, `interactive`, `draggable`, `cursor`, `focusable`, `tabIndex`, `hitArea`, `filters`, `mask` and `cullable` are assigned through the node's own setters after construction. Drawables also accept `tint`, `blendMode` and `anchor`. `scale`, `origin` and `anchor` take one number for both axes or an `{ x, y }` pair.
- **Signal handlers.** An `on*` prop adds the function to the signal of that name, so `onClick` goes to `button.onClick` and `onPointerDown` to `node.onPointerDown`. The handler is typed with that signal's arguments.
- **Children.** Children are added with `addChild` in the order written. Only containers take children: `<Sprite>` with children is a compile error, because a sprite is not a container. A container that restricts its children, such as `Graphics`, which takes only meshes, rejects the rest when the element is built.
- **`components`.** An optional list of [components](/ExoJS/en/guide/runtime/components/) attached with `addComponent`. See [Components](#components) below.
- **`ref`.** An optional callback that receives the finished instance, with its concrete type. Use it for calls that are not properties, such as `anchorIn` above.

Destroying the menu destroys its buttons, exactly as with `new`.

## Observable props

A prop can take an [observable value](/ExoJS/en/guide/runtime/observable-values/) instead of a plain one. JSX assigns its current value while it builds the node, then assigns every later change through the same setter until the node is destroyed. JSX still runs once: an observable change updates the existing node and never rebuilds or reconciles the tree.

<SourceSnippet source="examples/guides/jsx/game-hud.tsx" region="game-hud" language="tsx" title="examples/guides/jsx/game-hud.tsx" />

<SourceSnippet source="examples/guides/jsx/counter.tsx" region="counter" language="tsx" title="examples/guides/jsx/counter.tsx" />

- **Node properties**: all of them accept observables of their type, for example `visible={health.map(n => n <= 0)}`, `x={offset}` or `scale={other.scale}`.
- **Constructor options**: an option accepts an observable only when the instance has a writable property of the same name and type, such as `<Label text>` or `<Button label>`. The constructor receives the current value, and the property's setter receives later changes. An option that can only be set at construction does not accept an observable. TypeScript reports it.
- **Observable arguments**: an option whose own type accepts an observable is passed to the constructor as it is, not bound. JSX binds a constructor option only when the class has a property setter of that name; for a plain field it passes the observable unchanged.
- **Text**: `text` and `label` properties of type `string` also accept an observable number, converted with `String`, so `<Label text={health} />` works. Other properties get no conversion: `visible={health}` is a type error. `live`, the tagged template, builds text from several values.
- **Handlers**: `on*` props stay functions.

When an element fails, the failing node is destroyed and its bindings with it. In a `jsxTransaction`, every node of the failed tree is destroyed, so no binding survives.

## Existing instances

Put a node you already hold into the tree with braces. JSX adopts that instance: it is not cloned and not constructed a second time, and it keeps the handlers and state it already had.

<SourceSnippet source="examples/guides/jsx/scene-composition.tsx" region="scene-composition" language="tsx" title="examples/guides/jsx/scene-composition.tsx" />

Arrays (`{items.map(...)}`), `null`, `undefined` and booleans (`{open && <Panel />}`) are valid children. Strings and numbers are not, so pass text through a prop. A child that already has a parent is rejected rather than moved. Remove it from its parent first if moving it is what you mean.

A fragment, `<>...</>`, groups children without adding a level: the element that receives it adopts the fragment's children directly. A fragment written at the top level, outside any element, stays a plain `Container` holding its children. An element takes the fragment's children, so place each fragment once; placing it a second time is an error.

TypeScript checks all of it. It rejects unknown props, wrong option types, handlers whose parameters do not match the signal, children on non-containers, and classes that need an adapter. It also rejects a direct `Sprite` subclass whose constructor no longer takes a texture first, until that subclass declares its own adapter. An element function owns the children it receives: children it neither places nor destroys stay alive, so a function can keep them, for example to show a tab's content later.

<Callout type="info" title="Every JSX expression is a RenderNode">
TypeScript gives all JSX expressions one common type, `JSX.Element`, which ExoJS defines as `RenderNode`. `<Panel />` can go straight into `addChild`, but it is not typed as `Panel`. When the concrete type matters, construct the node with `new` and pass it in as an existing instance, or take it from a typed `ref`.
</Callout>

## Components

The `components` prop attaches each component of the list to the instance with `addComponent`, in list order:

<SourceSnippet source="examples/guides/jsx/reusable-widgets.tsx" region="components" language="tsx" title="examples/guides/jsx/reusable-widgets.tsx" />

TypeScript checks every component of the list the way `addComponent` does: a component written for one kind of node, such as `Pulse`, a `BehaviorComponent<Gem>`, is rejected on any other kind, even with `strict` off. To prepare a list elsewhere, type it `ComponentFor<Gem>[]`.

JSX attaches the components after the node properties, handlers and children, and before the `ref`. A component's `onAttach` therefore sees the node with its properties set and its children in place, and the `ref` can already read the components with `getComponent`. The components remain yours: a failed construction detaches them and never destroys them (see below). Attaching components in a `ref`, `ref={gem => gem.addComponent(new Loot(gem.size))}`, still works, for example for a component that needs the instance to be built.

## When construction fails

An element owns exactly one node: the instance it constructs. When a handler, a child attachment or the `ref` throws after construction, the element detaches the children it attached and destroys its own instance. It never destroys a JSX child, because JSX cannot tell whether a child is still yours: the compiler evaluates child expressions before their parent, so `<Button />` written inline and a button you built earlier, with JSX or with `new`, reach the parent the same way. When a constructor throws or a child is invalid, nothing has been attached yet and every child stays as it was.

Components from the `components` prop are treated like JSX children. The failing element detaches every component it attached, which runs the component's `onDetach`, and never destroys one, so you can attach it again. A component whose `onAttach` throws is not attached, and the components after it in the list are never attached. A component already attached to another node makes the element fail and stays where it was.

Children left behind by a failure are detached but alive. Garbage collection reclaims unreachable objects, but it does not call `destroy()`, so it releases no asset claims, signal handlers or other resources a node holds. Where a failed tree must not leave such nodes behind, build it inside `jsxTransaction`:

<SourceSnippet source="examples/guides/jsx/scene-composition.tsx" region="failed-tree" language="tsx" title="examples/guides/jsx/scene-composition.tsx" />

When the callback throws, every node JSX constructed during the call is destroyed, including siblings built before the failing one. A node passed as a JSX child that JSX did not construct in the transaction is detached first and never destroyed, and so is every component JSX attached from a `components` prop.

The transaction only knows what JSX attached. A node you attach yourself with `addChild`, in a `ref`, an element function or a `jsxConstruct` adapter, is part of the constructed node's subtree and is destroyed with it, like any child of a destroyed container. The same holds for a component you attach yourself with `addComponent`: destroying a node destroys its components. Attach nodes you keep after the transaction returns, or detach them in your own `catch` before rethrowing. Nodes created with `new` and never attached to a constructed node are left alone. Transactions nest, and construction inside them must be synchronous. A teardown that throws during cleanup is logged, and the original error is the one that reaches you.

## Serialization

JSX builds the same nodes as `new`, so `Prefab.from` and the scene serializers capture a JSX tree exactly like an imperative one. As always, they capture structure and data, not behaviour: signal handlers and `ref` callbacks are code, and are not serialized. Re-attach behaviour after `instantiate`, as with any prefab. See [Serialization & prefabs](/ExoJS/en/guide/runtime/serialization-and-prefabs/).
