# HUDs, menus, and widgets

A scene has two drawing surfaces with different responsibilities. `scene.root` contains the world you render explicitly. `scene.ui` contains screen-fixed UI that the engine renders automatically above that world. Put a score, health bar, or menu on `ui` so camera movement does not move the interface.

Core includes retained UI widgets. You do not need an extra package for buttons, panels, text inputs, sliders, or dropdowns. Use DOM UI instead when the surrounding application, accessibility requirements, browser-native controls, or document layout make it the better host.

The root owns the widgets and releases them with the scene. The button's signal belongs to that button. A subscription to an external application event or DOM object is a different lifetime and must be released explicitly.

Do not render `scene.ui` again from `draw`; that would duplicate the automatic overlay. Add world content to `root` and render that root normally when the scene also has gameplay.

## Layout relative to the host

`anchorIn` positions a widget relative to a UI box. Use edge anchors and margins for screen-fixed controls rather than hardcoded positions based on the initial canvas size. Layout follows logical canvas units, not backing-store pixels.

Use a `Stack` for a row or column and a `Panel` for its visual grouping. Keep the content's measured size and the panel's intended size consistent. An anchor is not a general flexbox engine: complex forms still need an intentional layout policy for small screens, long translations, and changing content.

A widget's UI dimensions, drawable bounds, origin, and text ink bounds are related but different. For example, rotating a panel around its center needs an appropriate origin; changing a sprite-style normalized anchor is not a substitute for understanding a container's content box.

## Choose widgets by task

| Task | Core building blocks |
| --- | --- |
| Read-only status | `Label`, `ProgressBar`, and optional icons. |
| A command | `Button` with a clear label and activation behavior. |
| A setting | `Checkbox`, `Slider`, or `Dropdown` as appropriate. |
| Text entry | `TextInput` or `TextArea`. |
| Grouped or overflowing content | `Panel`, `Stack`, and `ScrollView`. |

The API reference owns each widget's exact options, defaults, and events. The normal workflow is to create the widget, place it in a layout, subscribe to a meaningful user action, and update the displayed value when application state changes. Do not duplicate authoritative game state inside several unrelated widget callbacks.

`ProgressBar.value` represents normalized progress. Feed it actual health or loading state. A decorative timer that fills a bar is not evidence that an asset batch succeeded; [Loading and resources](/ExoJS/en/guide/assets/loading-and-resources/) explains settled, ready, and failed loads.

## Focus and modal interaction

Buttons can be operated through pointer input and keyboard focus. Test Tab navigation and Enter or Space activation as well as clicks. Disabling a widget should have an intentional effect on its appearance and interaction; hiding a container is not automatically a complete modal policy.

A modal interaction scope limits which nodes can receive interaction. Use one for a dialog that must block the underlying scene, retain its handle, and release it when the dialog closes. Restore the prior focus deliberately. An application-level keyboard listener can still bypass widget focus if your code routes it independently, so coordinate gameplay actions with the modal boundary.

Pause is a separate concern. A menu can be interactive while gameplay is paused only when its action availability permits that state. See [Pause menus](/ExoJS/en/guide/recipes/pause-menu/) rather than disabling all input globally.

## Text entry and scrolling

Text-input widgets use a DOM bridge for browser editing and composition. They are not equivalent to mapping gameplay key codes into characters. Test IME composition, selection, paste, focus transfer, and the host environment's DOM availability.

`TextArea` provides its supported text-entry model, not a browser word processor. Dropdown content follows its canvas hierarchy and clipping; do not assume a browser-style portal automatically escapes a clipped scroll view. Choose layout and clipping that leave the menu usable.

## World labels, minimaps, and DOM overlays

A world-space nameplate belongs with its world object or must be projected through the active view each frame. A screen-fixed quest panel belongs on `ui`. [Coordinates and views](/ExoJS/en/guide/runtime/coordinates-and-views/) explains that mapping and multi-view layouts.

A minimap is another rendering of world content, often into a smaller viewport or render texture. It is not a special health-bar widget. Use [Render targets](/ExoJS/en/guide/rendering/render-targets/) for its texture lifetime and [the minimap example](/ExoJS/en/playground/?example=render-targets/mini-map) for a complete composition.

A DOM overlay can provide native document semantics and controls while ExoJS renders the world. Define which layer owns pointer and keyboard input. Applying `pointer-events: none` to all DOM UI makes it noninteractive; use that only for genuinely display-only content.

## Accessibility is a product responsibility

Canvas drawing does not automatically create a semantic DOM tree for assistive technology. Provide appropriate DOM alternatives, labels, focus behavior, and input routes for the application's requirements. Test readable contrast, text scaling, touch targets, localization, and reduced-motion preferences rather than assuming that a rendered button supplies every browser-native affordance.

For a practical narrative interface, continue with [Dialogue and choices](/ExoJS/en/guide/recipes/ui-patterns/). Use the [UIRoot API](/ExoJS/en/api/uiroot/) and linked widget contracts for exact behavior instead of reproducing their full option tables in this Guide.
