# Scenes and lifecycle

An application is the long-lived host. A [`Scene`](/ExoJS/en/api/scene/) is a changeable activity inside it: a menu, level, cutscene, or editor view. Scene navigation keeps the application and canvas alive while changing the work they perform.

Start with one scene. Split scenes when activities need distinct activation or teardown, not merely because a class has become long. Ordinary helper objects and containers are sufficient for organizing work within an activity.

## From construction to activation

Register scene classes in `ApplicationOptions.scenes` and await `app.start(YourScene)`. The director constructs scene instances; do not pass a constructed instance in place of its class.

| Phase | Put this work here |
| --- | --- |
| Constructor and field initializers | Local state and objects that do not need the application or scene services. |
| `async load(data)` | Await the resources and other prerequisites required for activation. |
| `init(data)` | Synchronous setup using the attached scene services and loaded resources. |
| `fixedUpdate(delta)` | Fixed-step simulation, when the scene owns that simulation loop. |
| `update(delta)` | Variable-step state changes, input-dependent movement, and visual updates. |
| `draw(context)` | Submit existing state for rendering. |
| `async unload()` | Await scene-specific shutdown work after a successfully activated scene ends permanently. |
| `destroy()` | Synchronous cleanup of objects or external subscriptions owned by your code. |

`this.app`, `this.loader`, `this.inputs`, `this.systems`, and the other scene-bound services are unavailable during construction. They are available after attachment, including in `load`, `init`, and teardown hooks. A scene's activation-data type is the first `Scene` generic; the same activation data reaches `load` and `init`.

`load` and `unload` are awaitable. `init`, the frame hooks, and `destroy` must remain synchronous. Returning a promise from a synchronous hook does not turn it into another loading phase.

## Load before using required resources

Await essential assets in `load`, then build the scene in `init`. An acquisition through `this.loader` belongs to this scene's lifetime. An acquisition through `this.app.loader` belongs to the application's lifetime instead.

## Rendering is explicit

Adding nodes to `this.root` creates a hierarchy; it does not submit that hierarchy automatically. Render it from `draw` with `context.render(this.root)`. You can render a different root or several objects when the scene needs separate passes.

`this.ui` is different: the scene's screen-fixed UI layer is rendered automatically above its world content. Do not render it again from `draw`. Use [UI and widgets](/ExoJS/en/guide/runtime/ui-and-widgets/) for HUDs, forms, and focus handling.

Keep loading, object construction, and event binding out of `draw`. Repeating those operations every frame creates work and lifetimes unrelated to the scene's actual changes.

## Fixed steps and smooth presentation

Both update hooks receive **seconds**. `fixedUpdate` runs zero or more times before the variable update as the accumulated time permits. The default step is `1 / 60` second; `ApplicationOptions.fixedTimeStep` changes it. Catch-up is bounded, so a long stall is not a promise that every elapsed simulation step will eventually execute.

A constant timestep makes simulation timing consistent; it does not by itself guarantee deterministic results across machines, inputs, or physics implementations. For an automatically registered physics system, let that system step its world. Do not also call `world.step()` from `fixedUpdate`.

`app.frameAlpha` exposes the fractional remainder between fixed steps. The scene graph does not interpolate automatically. Keep previous and current simulation state and interpolate the rendered representation when you need smooth presentation between steps:

## Navigate, pause, or retain?

These are different operations:

| Intent | Mechanism |
| --- | --- |
| Leave an activity and start a fresh one | `app.scenes.change(TargetScene, options)` |
| Stop gameplay updates while keeping the current scene visible | `app.scenes.pause()` and `resume()` |
| Preserve a scene instance for later use | The director's retention and restoration API |
| Animate the visual handoff | A scene transition supplied to navigation |

Await navigation when subsequent work depends on its result, and handle a rejected navigation promise at the initiating boundary. A transition changes the presentation of the handoff; it does not remove loading or failure semantics. [Custom transitions](/ExoJS/en/guide/runtime/writing-your-own-transition/) explains the definition/session boundary when the built-in transitions are insufficient.

Ordinary pause stops scene updates and scene systems while allowing the scene to draw. Scene-bound services also have availability policies. In particular, `this.tweens` is **scene-owned**, but its default `when: 'always'` continues during ordinary pause. Choose an active-only policy for gameplay motion and an always or paused policy deliberately for a pause interface.

At this revision, tween availability is applied at pause/resume transitions rather than being re-evaluated when a tween is created. Do not assume that creating an active-only tween after the scene is already paused immediately freezes it. Retention suspension is a separate boundary: it suspends scene-bound activity until restoration.

## Ownership and teardown

The engine cleans up the scene graph, UI, and scene-bound services independently of your `destroy()` override. You do **not** need `super.destroy()` to preserve that internal cleanup. Scene-owned loader claims release automatically; manually unloading every texture in `unload` is neither necessary nor a substitute for choosing the correct owner.

Use `this.track(resource)` for a `Destroyable` your scene creates outside those automatically owned facilities. Tracked resources are destroyed in reverse registration order. External DOM listeners, timers, observers, and resources acquired directly at application scope still need an explicit ownership decision.

Do not make `unload` the only place that releases partially initialized work: it is not the successful-shutdown hook of a scene that never completed activation. Register ownership when acquiring resources, and use `lifecycleSignal` for cancellable asynchronous work. Scene teardown aborts that signal before unloading. An unrelated promise that ignores cancellation can still finish later; it must not then mutate a scene that has ended.

When a helper owns a shorter-lived scope, destroy the helper before its parent scene ends. Create child scopes only while their parent is live. [Loading and resources](/ExoJS/en/guide/assets/loading-and-resources/) covers independent claims and nested lifetimes.

## Check the boundary first

An empty canvas often means the root was never rendered or the canvas was never mounted. An undefined service usually means it was accessed during construction. A surviving sound, request, or tween often means it was created at application scope rather than scene scope. Inspect those boundaries before adding manual cleanup throughout the code.
