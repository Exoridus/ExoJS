# Serialization & prefabs

ExoJS can turn a scene-graph subtree into plain JSON and rebuild it later. The serializer captures **data and structure** — transforms, visuals, asset references, and the tree shape — **not behaviour**. Update logic, signal handlers, tweens, and systems live in your `Scene` / `System` code and are re-attached after a load. That boundary keeps the format small and matches the engine's code-first design.

Use it for level/scene layouts, reusable prefabs, the structural half of save games, editor save/load, and snapshot tests.

## Serializing a scene

[`Scene.serialize()`](/ExoJS/en/api/scene/) returns a JSON-able descriptor; [`Scene.deserialize()`](/ExoJS/en/api/scene/) rebuilds the scene's `root` (and `ui` layer, if present) from one. Saved references name resources rather than embedding their bytes. Readiness is a per-serializer contract: a format-3 Sprite can attach and load lazily, while BitmapText and several other rendering types require resident assets. Use the [matrix below](#asset-readiness-by-serializer) before choosing when to restore.

```ts
import { Scene } from '@codexo/exojs';

declare const scene: Scene;

// Capture the current layout as plain JSON.
const data = scene.serialize();
const json = JSON.stringify(data);

// ...later, after satisfying the serializers' readiness requirements, restore it.
scene.deserialize(JSON.parse(json));
```

A freshly-constructed node serializes to just its `type` tag — only non-default fields are written, so the JSON stays compact.

<Callout type="info" title="Structure is captured, behaviour is not">
Serialization records data and structure — transforms, tints, blend modes, frames, tree shape, and asset keys. Live and behavioural pieces (a `mask` node, post-process `filters`, `Geometry` clip shapes, custom materials, update logic) are skipped, so re-attach them in your `Scene` code after loading.
</Callout>

[Components](/ExoJS/en/guide/runtime/components/#saving-scenes-with-components) can persist their registered data. `app.serializers.components.register` associates an exact class with a stable type id, parser, optional version/migrations, constructor callback, and serializer. Reads construct fresh detached components, resolve local links, and then attach them. Existing methods run on those new instances; callbacks and arbitrary closures are not saved.

Unregistered components throw. `{ omitComponents: true }` omits all components deliberately, including registered ones. `Scene.serialize()` also rejects components attached directly to its special root or UI layer; components on their descendants are supported. Component registrations belong to that registry and do not use its node-serializer fallback chain.

## Prefabs

A [`Prefab`](/ExoJS/en/api/prefab/) captures a configured subtree once and stamps out independent copies — the data-driven counterpart to building objects in a code factory. There is no re-serialization per instance.

```ts
import { Prefab, type SceneNode } from '@codexo/exojs';

declare const coin: SceneNode;

const prefab = Prefab.from(coin);

for (let i = 0; i < 10; i++) {
  const instance = prefab.instantiate();
  instance.setPosition(i * 32, 0);
}
```

`prefab.toJSON()` and `Prefab.fromJSON(document)` round-trip a prefab through disk or the network. `toJSON()` writes a versioned document — `{ version, root }`, the same frame a serialized scene carries — and `fromJSON()` validates it, so a prefab written today can still be read by a later build.

## Persisting saves

The engine ships the save **primitives**, not a save *system*: [`Scene.serialize()`](/ExoJS/en/api/scene/) captures a scene's structural state, and a `KeyValueStore` persists it under a slot key. Slot naming, profiles, autosave, and metadata are game-specific, so pair this with your own game-state persistence (score, inventory, quest flags) for a complete save system — the serializer owns the *world layout*, your code owns the *gameplay variables*.

```ts
import { WebStorageStore, type Scene, type SerializedScene } from '@codexo/exojs';

declare const scene: Scene;

const store = new WebStorageStore(localStorage, { prefix: 'mygame:' });

await store.set('slot-1', scene.serialize()); // serialize + persist

const data = await store.get<SerializedScene>('slot-1'); // fetch
if (data) scene.deserialize(data); // restore
```

Choose the backend by capability: [`WebStorageStore`](/ExoJS/en/api/web-storage-store/) for small synchronous JSON saves, [`IndexedDbKeyValueStore`](/ExoJS/en/api/indexed-db-key-value-store/) for large or binary saves, [`MemoryStore`](/ExoJS/en/api/memory-store/) for tests. They share one `KeyValueStore` interface, so swapping is a one-line change.

## Asset readiness by serializer

| Document or node | Resolution and failure behavior | What the caller owns |
| --- | --- | --- |
| Format-3 `Sprite` with a typed texture reference | Constructs a path-backed handle without fetching. Attaching the Sprite to a scene starts acquisition; it draws empty until ready. | The attached node's scene claim. A detached prefab instance does not load merely because it was instantiated. |
| Legacy/v2 Sprite references, including plain keys | Uses the resident `resolveAsset` path; a missing resource resolves to `null` and can warn. | Preload through the intended scene/app scope before restoration. |
| `BitmapText` | Requires a resident `BmFont`; restoration throws when it is missing. | Preload the font; its loader-owned dependency scope owns atlas pages. |
| `Mesh`, `NineSliceSprite`, `RepeatingSprite`, `AnimatedSprite` | Use resident `resolveAsset`; a missing texture can warn and resolve to `null`. They do not inherit the format-3 Sprite loading path. | Preload the needed texture and keep its owner alive. |
| Custom serializer using `ctx.resolve` | Creates/reuses a deferred reference without fetching. Scene deserialization reserves it in the scene scope; direct prefab construction has no implicit scene context. | Pass the intended loader/registry, then explicitly acquire or attach through a consumer with an acquisition contract. |
| `Text` | Restores style/layout data such as the font family, not browser FontFace registration or an atlas snapshot. | Deploy and load the font before reliable custom-font layout. |

A `Scene.deserialize` call supplies both `app.serializers` and the scene's asset scope. `prefab.instantiate(app.loader, app.serializers)` supplies those two explicit arguments but does not attach the returned node or silently give it the scene's scope. Custom deferred references from a direct `Prefab.instantiate(app.loader, ...)` call are reserved in a child of the application loader scope, so destroying only the returned node does not release those application reservations. `Scene.deserialize` reserves them under the scene scope instead. A format-3 Sprite constructs its own idle texture handle and acquires it when attached to `scene.root`/`scene.ui`. An asset kept resident by a different scene may disappear when that owner ends, so a successful resident lookup is not a substitute for your own claim.

These differences also apply to prefabs created from JSON. Reading a legacy document preserves its source version; calling `toJSON()` does not silently upgrade its asset semantics. Await required assets and handle restoration errors at the save/navigation boundary.


## Format 3 and typed asset references

Scenes and prefabs now write `version: 3`. A texture is stored as a typed reference, `{ "$type": "texture", "source": "hero.png", "options": { ... } }`, which also keeps persistable settings such as the sampler. Nodes in one document can point at each other with local `$id` and `$ref` links. Documents written by earlier versions (a plain string or `{ source, options }`) still read with their original serializer semantics. Deferred resolution depends on the individual serializer and on whether restoration is scene-bound or a direct prefab call.

Asset types you register with `assetTypes` or `app.assets.define()` are saved under their `type` string, so choose one that you can keep stable. See [Migrating to path-based assets](/ExoJS/en/guide/assets/migrating-to-model-b-plus/).

## Custom node types

Your own [`SceneNode`](/ExoJS/en/api/scene-node/) subclasses become serializable by registering a serializer with [`registerSerializer`](/ExoJS/en/api/serialization-registry/). The framework writes the common transform/visual fields and the type tag; your serializer only handles its own fields.

## Video sources

A serialized document is untrusted input, and restoring a `Video` node starts a network request for its `src`. By default `Scene.deserialize()` and `Prefab.instantiate()` accept only same-origin HTTP(S) and `blob:` sources and throw on anything else, including cross-origin and `data:` URLs. Documents that reference other hosts must opt in per source with `allowVideoSource`, which receives the resolved `URL` and can approve any scheme, including `data:` and `javascript:`, so check the protocol and host yourself:

```ts
import { Scene, type SerializedScene } from '@codexo/exojs';

declare const scene: Scene;
declare const document: SerializedScene;

scene.deserialize(document, { allowVideoSource: source => source.hostname === 'cdn.example.com' });
```

The check looks at the URL only, so it cannot see a same-origin redirect that leads elsewhere.

## What is not captured

The format deliberately stops at structure:

- **Behaviour** — update logic, signal handlers, tweens, input bindings, systems. Re-attach these in code after a load.
- **Live/heavy references** — a node `mask` that points at another node, post-process `filters`, a `Geometry` clip shape, and custom materials are skipped (with a one-time warning). Transform, tint, blend mode, frame, and asset references all round-trip.
- **Runtime-only assets** — a `RenderTexture` or other resource not loaded through the `Loader` has no source key, so the reference is omitted.

Every value the serializer writes is JSON-serialisable; caches, matrices, and dirty flags never appear in the output.
