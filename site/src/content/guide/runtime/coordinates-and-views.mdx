# Coordinates, cameras, and split views

A position needs a coordinate space. Most placement and camera bugs come from passing a valid number to an API that expects a different space, not from an inaccurate transform.

| Space | Meaning |
| --- | --- |
| Local | Coordinates relative to a node's parent or an object's own geometry. |
| World | Coordinates after the parent transform chain. |
| Logical canvas | The application's design space, from `(0, 0)` to `(app.width, app.height)`. |
| Backing pixels | The actual render-surface resolution after sizing and pixel ratio. |

`node.setPosition(...)` sets a **local** position. It coincides with world position only when the parent transform makes that true. A sprite's anchor or a container's origin affects where its geometry lies relative to that position; neither removes the parent transform.

## A view maps world to canvas

A [`View`](/ExoJS/en/api/view/) chooses the world region to show and the part of the canvas to paint. Its center is a world-space point, its size describes the visible world extent, its rotation turns the camera, and its viewport selects a normalized canvas region.

With center `(400, 300)` and size `(800, 600)`, an unrotated, unzoomed full-canvas view shows world coordinates from `(0, 0)` to `(800, 600)`. Move its center to scroll; change its zoom to show more or less world. `setZoom(2)` shows half the world extent at twice the apparent scale.

Use `context.view` for the scene's normal view or pass a dedicated view to a draw. `context.screenView` supplies a screen-fixed view for explicit overlays. `scene.ui` already uses the automatic UI path and should not be rendered again manually.

## Follow a world-space target

A view can follow an object with `x` and `y` coordinates. Those values must describe the intended world point. Following a deeply parented node's local position as though it were world position produces an incorrect camera target.

For smoothing, keep a separate world-space camera target and move it toward the subject in `update`. A frame-rate-aware exponential weight is `1 - Math.exp(-response * delta)`; unlike an unbounded `response * delta` weight, it does not overshoot simply because one frame was long. The [camera-follow recipe](/ExoJS/en/guide/recipes/camera-follow-and-parallax/) combines follow and parallax without changing the subject's simulated position.

## Convert input using the same view

In split-screen, first choose the viewport under the pointer, then use that viewport's view. Converting with the other player's camera can yield a plausible point in the wrong part of the world. If hit testing needs a child's local coordinates, apply the appropriate world-to-local conversion afterward.

Do not multiply pointer coordinates by DPR to repair a camera mismatch. The input system already supplies logical canvas coordinates; backing pixels are a rendering detail.

## Draw one world through multiple views

Keep one world state and give each player a separate `View`. Advance the world once, then submit it through each view:

Create the views during setup, update their centers from the players' world positions, and call `drawSplitWorld` from the scene's `draw`. The left viewport covers `[0, 0, 0.5, 1]`; the right covers `[0.5, 0, 0.5, 1]`. Viewport values are normalized fractions of the render surface, not world distances.

The helper receives existing world content. It does not create players, bindings, or a second simulation. On resize, update each view's world size to match the intended aspect ratio while keeping its normalized viewport. Let the application's sizing policy determine the logical dimensions.

Passing `{ view }` per draw keeps the choice explicit. If advanced code mutates raw backend state instead, it must restore the relevant view, viewport, target, and clipping boundaries before later work. Do not add manual viewport resets to normal scoped draws merely because an older raw-state example needed them.

## HUDs, minimaps, and picture-in-picture

For a global HUD, use `scene.ui` or render explicitly with `context.screenView`. For player-local HUDs, define each player's UI region deliberately instead of letting the last world viewport leak into the overlay.

A minimap or picture-in-picture view follows the same model: choose a second camera and a smaller viewport, or render into an owned texture for later composition. A render texture adds a lifetime, resize policy, and sampling boundary; see [Render targets](/ExoJS/en/guide/rendering/render-targets/).

<ExamplePreview chapter="application-scenes" slug="picture-in-picture" />

Multiple views repeat relevant rendering work and may cover different objects or pixel areas. They do not necessarily double total frame time. Measure traversal, culling, effects, and fill cost for the actual composition while keeping simulation independent of the number of views.
