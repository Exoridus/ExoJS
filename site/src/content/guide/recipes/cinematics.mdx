# Cinematics

A cinematic (or cutscene) is a choreographed sequence where the camera moves, dialogue appears, characters animate, music swells, and the player's input is temporarily suspended, all driven by timing. ExoJS provides tweens and `TweenSequencer` for animation timing, `View` for camera movement, scene-owned audio for music, and `app.scenes.change(...)` for transitioning between game states. This recipe coordinates a short sequence with independent tweens and delays.

## Approach

A cinematic is a scene. Tweens drive its camera pan, title reveal, character entrance, and music fade. Create them through `this.tweens` and play music through `this.audio` so they stop when the scene ends. Keep references to the sequence's own tweens so skip can stop them without interrupting animation elsewhere in the application. `CinematicScene` below implements the visuals; `CutsceneFlowScene` extends it with skip input and a return to gameplay.

The key technique: **tween chains and delays**. Each tween starts at a specific time offset. Together they form a timeline:

## The timeline

The sequence above runs as follows:

| Time | Event |
|------|-------|
| 0.0s | Shutter bars start opening. Camera begins panning. Music starts fading in. |
| 1.1s | Boss begins scaling up from 0.4x to 2.1x. |
| 1.6s | Title text begins revealing character-by-character. |
| 2.0s | Camera pan completes. Music reaches its target volume. |
| 2.6s | The full title is visible. |
| 2.9s | Boss reaches its final scale. |
| 3.5s | The flow scene starts closing the shutter bars. |
| 4.1s | The bars are closed; the return to gameplay begins. |

Each tween operates independently — they don't need to know about each other. The `delay()` method offsets the start time. The `.onUpdate()` callback on the title tween drives the character reveal, mirroring the typewriter pattern from [UI patterns](/ExoJS/en/guide/recipes/ui-patterns/).

## Skip support

Press Space, Enter, or gamepad Start to stop the sequence, snap its visible state, and return to gameplay with a fade. The scene-owned input binding is removed automatically when the scene ends:

## Orchestrating beats with a `Sequencer`

When beats depend on each other - wait for a sound, then for the player, then hand control back - write them as one generator function and play it on a `Sequencer`. The sequencer is a system: add it to `this.systems` and its sequences advance in the scene's update phase on the scene's own delta. `yield* context.wait(0.3)` waits scene time, not wall-clock time, and every sequence freezes while the scene is paused or retained. A sequence's code runs only inside that phase, synchronously, never in a promise continuation, and `play` never runs it at once: it starts on the sequencer's next tick, so a sequence played while the scene is still loading, paused or retained takes nothing over until the scene runs.

<SourceSnippet
  source="examples/showcase/boss-intro-sequence.ts"
  region="boss-intro-sequence"
  language="ts"
  title="examples/showcase/boss-intro-sequence.ts"
/>

- Every wait is delegated with `yield*`, and its result is the value of the expression: `const [winner] = yield* context.waitFor(roundEnded)`, `const delta = yield* context.nextFrame()`.
- `context.waitFor` takes a `Signal`, a condition, a handle, a promise or an operation. A condition is first checked on the tick after the wait began, so `() => confirm.pressed` waits for a fresh press of the action - a key already held, or one the player rebinds away from, does not count.
- `context.all([...])` runs branches side by side until every one completes; `context.race([...])` stops at the first and cancels the losers it started. A branch is a generator function of its own context, or a handle. `context.start(branch)` starts one in the background and returns a handle to join later with `yield* context.waitFor(handle)`; it is cancelled if it is still running when its owner ends, and its failure is thrown into its owner.
- Calling another generator with `yield* step(context)` nests it in the same flow.
- Native actions plug in through the `SequenceOperation` contract: `tweenOperation(tween)` starts a tween, completes the wait when the tween completes and stops the tween if the step lets go first.

`sequencer.play(...)` returns a handle. `handle.cancel()` is the skip: every branch stops at once, `finally` blocks run synchronously, innermost first, and owned operations such as the pan tween are stopped. Cancellation is cooperative - it closes the generator where it waits - so a promise the sequence handed to other code keeps running; pass `context.signal` to APIs that accept an `AbortSignal`. Ending the scene cancels its sequences the same way, and each `play` is an independent run, so replaying is playing again. `await handle.done` resolves with how the run ended - completed, cancelled or failed - without changing when anything runs.

The sequencer coordinates, it does not own the camera, input or audio for you. Give back what a sequence takes in its `finally`: the input scope it pushed, the camera follow it cleared. A voice started while audio is still locked never starts and never ends, so wait for its `onEnd` in a race against a bound.

## When not to build a cinematic system

For a single boss intro, one scene with delayed tweens is sufficient. For sequential beats, use `this.tweens.createSequencer()` to obtain a scene-owned `TweenSequencer`: `then(tween)` adds a stage, `then([a, b])` runs tweens together, and `wait(seconds)` inserts a pause. Build a separate cutscene authoring layer only when your content needs more than these timing primitives.
